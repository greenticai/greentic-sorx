# Greentic Reuse Audit

| Capability | Existing repo/crate/module | Reuse decision | Notes |
| --- | --- | --- | --- |
| `gtc` extension discovery | `greentic/src/bin/gtc/extensions.rs`, `greentic/src/bin/gtc/router.rs`, `greentic/src/bin/gtc/process.rs` | Direct SORX invocation aligned; `gtc sorx` blocked on `gtc` route | Existing `gtc` code supports fixed passthroughs for `dev`/`op`/`wizard`/`setup` and extension handoff files for wizard/setup/start. It does not currently expose generic `gtc <name>` discovery for arbitrary `greentic-<name>` binaries, so PR 10 documents the gap and keeps `greentic-sorx` directly invokable with a `gtc`-compatible command shape. |
| Direct `greentic-*` executable invocation | `greentic/src/bin/gtc/process.rs`, multiple repos publishing `greentic-*` binaries | Reuse naming convention | Binary is named `greentic-sorx`; release metadata supports `cargo install` and `cargo binstall`. |
| `.gtpack` read/write/doctor APIs | `greentic-pack`, especially `crates/packc` and docs under `greentic-pack/docs/` | Minimal local runtime reader added in PR 02 | Existing Greentic pack tooling covers pack build/doctor/inspect behavior, but this repo does not currently depend on a small stable publishable runtime-reader API. `greentic-sorx-pack` implements only the SORX validation/inspection subset and should be replaced or narrowed if a shared API becomes available. |
| Pack manifest and lock parsing | `greentic-pack`; SoRLa docs mention local manifest/lock writers in `greentic-sorla/docs/sorla-gtpack.md` | Minimal local model added in PR 02 | `greentic-sorx-pack` models only the manifest/lock fields needed to load and validate SORX runtime packs. |
| Asset lookup inside `.gtpack` | `greentic-pack` pack-format and doctor logic | Minimal local reader added in PR 02 | Local lookup is limited to `.gtpack` ZIP entries and allowed `assets/sorla/**` / `assets/sorx/**` paths. It does not add loose-folder runtime support. |
| Canonical CBOR helpers | `greentic-pack`, `greentic-sorla` artifact docs | Use standard CBOR reader locally for now | PR 02 uses `ciborium` directly for `pack.cbor` and `pack.lock.cbor` until a shared helper is available. |
| `greentic-qa` question/schema/answers flow | `greentic-qa`, especially sibling `qa-spec` and `greentic-qa-lib` crates | Small local adapter added in PR 03; reuse later | `../greentic-qa` exposes useful validation/normalization concepts, but this publishable repo cannot depend on a sibling path crate and does not currently have a stable registry dependency wired. `greentic-sorx-core` implements a small JSON-schema-oriented adapter for required/default/enum/type checks and deterministic normalized output. Interactive prompting is intentionally reported as not wired yet. |
| `gtc start --schema` / `--answers` patterns | `greentic-start`, `greentic-pack` wizard, `greentic-sorla` docs | Follow command shape | PR 03 implements `greentic-sorx start <pack.gtpack> --schema`, `--answers`, `--dry-run`, and `--emit-answers` behavior. |
| Config manager / answer envelope patterns | `greentic-qa`, `greentic-config`, `greentic-pack` wizard | Minimal envelope added in PR 03 | `greentic-sorx-core` emits `greentic.sorx.start.answers.normalized.v1` and `greentic.sorx.start.plan.v1` JSON; future work should align this with a shared Greentic QA/config envelope once available. |
| Logging/tracing conventions | `greentic-telemetry`, widespread `tracing` use | Reuse later | No runtime logging subsystem is introduced before runtime behavior exists. |
| HTTP server conventions | Existing Greentic repos use `hyper`; PR 05 allows `axum` if no convention fits | Minimal local adapter added in PR 05 | PR 05 implements a dependency-light `std::net` HTTP adapter around the PR 04 runtime path. It keeps route generation and request handling isolated so a later Axum/Hyper adapter can replace it without changing provider execution. |
| MCP server/tool conventions | `greentic-mcp` and related MCP repos | Local adapter added in PR 07; transport reuse later | PR 07 loads `assets/sorla/mcp-tools.json`, validates tool references, exposes resolved tool metadata, and routes adapter tool calls through `SorxRuntime`. A full MCP server transport remains future work so it can align with shared Greentic MCP conventions instead of inventing an incompatible server surface. |
| Provider registration patterns | `greentic-messaging-providers`, `greentic-state`, `greentic-secrets-lib`, provider docs | Local trait added in PR 04; binding resolver added in PR 08; reuse later | PR 04 defines the small `SorStoreProvider` trait, `ProviderRegistry`, and deterministic in-memory provider needed for the SORX runtime core. PR 08 adds `BindingResolver`, tenant/pack/version provider namespaces, and a FoundationDB adapter boundary. It avoids taking a shared provider dependency until the cross-repo SORX provider API is stable. |
| FoundationDB provider | `../greentic-sorla-providers/providers/provider-foundationdb` | Adapter boundary added in PR 08; direct integration blocked | The sibling provider currently exposes event/projection traits with local/dev in-memory behavior and is `publish = false`; it does not expose the CRUD-shaped SORX store contract. SORX registers `foundationdb` through an unavailable adapter that preserves the config boundary and returns a clear `provider_unavailable` error. See `docs/audit/provider-foundationdb-gap-pr08.md`. |
| Secrets/OAuth references | `greentic-secrets`, `greentic-oauth`/shared Greentic secret conventions where available | Reuse later | Startup answer validation rejects inline secret-like values; external secret/OAuth resolution remains future work. |
| Audit/event sink conventions | `greentic-telemetry` audit helpers, tenant-manager audit docs, events repos | Local sink added in PR 06; reuse later | PR 06 defines `AuditSink`, `SorxAuditEvent`, and stdout/memory/disabled sinks locally so runtime policy/provider behavior can emit structured events. Future work should align this with shared Greentic telemetry/events APIs. |
| CI/local check conventions | Current repo `ci/local_check.sh`; broader Greentic repos use fmt/clippy/test/package/coverage workflows | Already aligned | Local check remains the single developer entrypoint and now runs workspace checks. |
