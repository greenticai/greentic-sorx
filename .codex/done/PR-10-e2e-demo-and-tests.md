# PR 10 — greentic-sorx: local integration coverage for generic env runtime-host flow

## Repo

`greenticai/greentic-sorx`

## Status from current code

The end-to-end `gtc env` commands, setup flow, start orchestration, and bundle doctor belong to sibling repos. They should not be implemented in this repository.

This repo can still prove the Sorx side of that flow by exercising the artifacts and APIs those tools will use:

- `greentic-sorx runtime-host manifest`
- `greentic-sorx start` loading `runtime-config.json`
- `/admin/v1/*` runtime-host endpoints
- runtime-config revision/traffic snapshots
- stack control and observer pipelines
- admin surface registration and admin control/observer pipeline

## Goal

Add Sorx-local fixtures and integration tests that demonstrate Sorx can be driven by a generic environment runtime snapshot and packaged as a runtime-host ext-pack.

The tests must avoid invoking `gtc env` directly. Cross-repo tests for `gtc wizard/setup/start/env` should live in `greentic`, `greentic-start`, `greentic-setup`, `greentic-bundle`, or a demo repo.

## Local fixture

Add a generic fixture under the Sorx test tree with:

- A runtime-host manifest generated by `runtime-host manifest` or an equivalent helper.
- A `.gtpack` or loaded pack fixture already compatible with Sorx tests.
- A `runtime-config.json` using `greentic.runtime-config.v1`, two revisions, and basis-point weights.
- Optional extension binding metadata if PR 05 has landed.

The fixture should use generic deployment/revision names in the runtime-config where possible. Pack fixture names may still mention Sorx/Sorla because they identify this repo's concrete implementation.

## Integration scenarios

### Runtime-host manifest

Run the CLI command or helper and assert:

- `schema` is `greentic.sorx.runtime-host-pack.v1`.
- `env_binding.slot` is `deployer`.
- `env_binding.kind` is `greentic.deployer.sorx@0.1.0`.
- Capabilities offer `greentic.cap.runtime.host.v1`.
- Contracts include admin, health, deployments, traffic, and invoke.

### Start from runtime config

Start/build `HttpRuntime` with a `runtime-config.json` discovered from the same paths `greentic-start` will materialize:

- `runtime-config.json`
- `.greentic/environments/<env>/runtime-config.json`
- `environments/<env>/runtime-config.json`
- `$HOME/.greentic/environments/<env>/runtime-config.json`

Assert `/admin/v1/deployments` exposes the staged generic deployment/revision snapshot and weights.

### Admin lifecycle contract

Exercise `/admin/v1/deployments/stage`, `warm`, `activate`, `traffic`, `drain`, and `deactivate` in one integration-style test and assert:

- lifecycle transitions use `staged`, `ready`, `draining`, and `inactive`;
- traffic weights are basis points and must sum to `10000`;
- invalid revision IDs and invalid traffic sums return structured Sorx errors.

### Control and observer contract

Use test hook implementations rather than external extension packs:

- `pre_call` deny prevents provider invocation and emits denied observer event.
- `pre_call` and `post_call` patches mutate stack request/response.
- successful stack call emits started/completed events with environment/runtime/deployment/call IDs.
- failed stack call emits failed event once PR 05 failure coverage lands.

### Admin surface contract

Register an admin surface and assert:

- `/admin/v1/admin-surfaces` lists it deterministically;
- generic admin requests run through `pre_admin` and `post_admin`;
- observer receives started/completed/denied/failed admin events as applicable.

## Guardrails

- Do not add `gtc env` command handling in this repo.
- Do not hardcode sibling repo behavior in Sorx tests.
- Do not add Sorx-specific capability slots.
- Do not key generic runtime dispatch on the string `sorx` outside Sorx-owned descriptor and metadata.

## Acceptance criteria

Sorx has local integration coverage showing it can be selected as a generic runtime-host/deployer ext-pack and driven by environment runtime-config/admin APIs, while cross-repo `gtc env` UX remains owned by the sibling repos.
